# 设计旅程 · 技术选型：为什么是 Rust，为什么少用 LLM

> 这一章讲两个硬约束下的技术决策。它们不来自"喜欢什么技术"，而来自我们想服务的人：
> **个人用户、家用电脑、不是开发者**。

## 先想清楚：我们为谁做

赛博生命的典型场景是**个人的长期陪伴**（或 AI 主播）。要把陪伴真正交到普通人手里，
有两个硬性条件：

1. **必须能自部署**——理由见 [为什么必须自部署](self-host.md)：隐私、可靠性、以及
   "陪伴很久的东西不能因为公司倒闭就消失"；
2. **目标硬件是家用笔记本电脑**——跑 AI 应用时，这是一台资源受限的设备；
3. **用户不是开发者**——大部分人没有能力、也不愿意在命令行里折腾环境。

这三条，直接决定了下面两个选择。

## 为什么是 Rust

最初我们考虑过常见的 Python / TypeScript，但最终选了 Rust，理由非常实际：

| 需求 | Rust 怎么满足 |
|------|--------------|
| **一键运行** | 编译为单个二进制，双击就能跑——不依赖 Python 解释器、不依赖 Node 环境 |
| **资源占用小** | 没有运行时解释器的开销，内存占用低，适合家用笔记本 |
| **性能** | 理论性能高，图算法（PPR）、向量计算都吃性能 |
| **鲁棒性** | 内存安全 + 强大的类型系统，编译期消灭一整类 bug——一个要长期陪伴用户的
  服务，稳定是第一位的 |

"编译为二进制、不依赖解释器环境"这一点，对"给普通人用"是决定性的：用户不需要装
Python、不需要配环境变量、不需要处理依赖冲突——拿到一个文件，双击运行。

## 为什么尽可能少用 LLM

这是 SoulMem 最重要的一条设计原则：

> **能不用 LLM，就不用 LLM。让 LLM 只在最关键的地方发挥作用。**

原因非常现实：

- **本地部署**：个人用户跑不动足够强的模型，同时还要轻松地用电脑干别的；
- **API 烧钱**：token 消耗是真金白银。角色扮演场景的**缓存命中率通常很低**（每次对话
  都是新内容），这笔开销无法忽视；
- **延迟**：LLM 的响应是秒级的，频繁调用会拖垮对话体验。

所以 SoulMem 的策略是：**用精心设计的数据结构和算法，完成绝大部分记忆工作；LLM 只做
那些真正需要"理解"和"生成"的事**——比如：

- 把一段对话**摘要/拆解**成记忆节点（巩固）；
- 对**被遮罩的记忆做猜补**（遗忘修订）；
- （外部）根据检索结果生成角色的回复。

而检索、联想（PPR）、相似度、遗忘衰减、连接强度调整——这些全部是确定性算法，零 LLM
调用。

> 这个原则甚至影响了架构：SoulMem 的记忆系统是"有状态的工作图"，LLM 只是其中的一个
> **末端执行器**，而不是大脑本身。好处是可控、省 token、且对工具调用能力弱的模型也
> 普适——角色扮演更看重性格遵循能力，不能依赖每个模型都有很强的工具调用能力。

## 小结

- **为谁做**：个人用户、家用电脑、非开发者 → 自部署 + 资源受限 + 低门槛；
- **Rust**：一键运行（二进制）、资源占用小、性能高、鲁棒；
- **少用 LLM**：成本、延迟、本地算力三重约束 → 数据结构与算法为主，LLM 只做关键环节。
